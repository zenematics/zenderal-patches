# UnifiedWaterEnderal

- **Source:** `src/UnifiedWaterEnderal/` (generated: `tools/00-scan-vyn-water.py` → `tools/01-build-vyn-full-extend.py`)
- **Ships:** `Zenderal - Vyn Full Extend.esp` (generated binary, not committed; MO2 mod `Zenderal - Vyn Full Extend`)
- **FormID block:** `0x800–0x6606` (new CELL + LAND pairs). **Full plugin, not ESL** (about 24,000 new records).
- **Pillar:** modern visuals

## Why

With Bottled Shaders' **Unified Water** on (a Community Shaders feature), Vyn's distant sea had cell-sized strips and
blocks with no water, everywhere along the coasts (curator's screenshots, 2026-10-28).

**[verified in Community Shaders' source, `src/Features/UnifiedWater*`]** Unified Water disables the vanilla LOD water
add loops. When a terrain LOD chunk attaches (`BGSTerrainBlock::Attach` hook), it **removes all of that chunk's
vanilla LOD water** and adds one plane per cell from its cache. A chunk with no cache data at all keeps its vanilla
water. The cache (`WaterCache::BuildDiskCache`) only has a cell when some plugin gives it a CELL **and** a LAND
record (`VHGT`: water shows where the cell's water height is above its lowest land point), inside the WRLD's
`NAM0`/`NAM9` bounds. Skyrim gets away with it because Bottled ships `Tamriel_precache.wpc`, built from sheson's SSE
Terrain Tamriel Full Extend. That path is hard-wired to the EditorID `Tamriel`.

**[verified on the live load order, `tools/00`]** 84 plugins carry Vyn. Every cell that has records qualifies
(Vyn's default water `NAM2` = `DefaultWater 000018`, default water height 0, default land height −2048). But inside
the 26 LOD32 chunks that hold any Unified Water cell, **12,246 cells had no data**: 11,825 with no CELL at all, 421
CELLs without LAND (416 `Skyrim.esm`, 5 FS), and some outside the bounds (`NAM0` stopped at cell −69, −55). Those were
the strips.

First symptom, the same day: no distant water at all, because the cache had no `Vyn_cache.wc` (17 of 18 worldspaces
built). Bottled Shaders menu → Unified Water → Debug → **Regenerate Caches** built it. See
[`mod-gotchas.md`](../modlist/mod-gotchas.md).

## What it does

Enderal's Full Extend for that purpose, generated by `tools/01` from `tools/00`'s scan:

- **11,825 new CELLs** (`HasWater`, no `XCLW`, so Vyn's default water height 0) with a **flat LAND at −2048**, Vyn's
  default land height. That is what the game and the terrain LOD already assume for a cell with no LAND, so nothing
  visible moves; it only gives Unified Water something to read.
- **421 existing CELLs without LAND:** the winning record (base Enderal or FS) copied **byte for byte**, plus the same
  flat LAND. Their form indices match this plugin's masters (`Skyrim.esm`, `Update.esm`, FS); the generator refuses
  any other owner. Placed references are never copied.
- **The Vyn WRLD:** `Occlusion.esp`'s winning record byte for byte, with `NAM0` lowered to cell −96, −64 (Unified Water
  skips cells outside the bounds). Its form references (`XLCN`, `CNAM`, `NAM2`, `NAM3`) are all Skyrim.esm's.

Only cells in chunks that already get Unified Water are filled; chunks with no water data keep vanilla LOD water.
Written as binary because the Spriggit YAML for 12,000 landscapes would be about 230 MB. Checked by serializing the
output with Spriggit 0.40.0: every cell and LAND reads back, all 12,246 LANDs at offset −256 (×8 = −2048).

## Load order

**Load it LAST**, after `Occlusion.esp`: it carries the Vyn WRLD record, and DynDOLOD's `Occlusion.esp` is its last
overrider. **Regenerate** (`tools/00` then `tools/01`) after a DynDOLOD/Occlusion run or when any plugin adds or
removes Vyn cells. Unified Water rebuilds its cache by itself when the load order changes; if the sea still has gaps,
use Regenerate Caches.

## Status

Built and enabled 2026-10-28 in Ultra: MO2 mod at the top of `modlist.txt`, plugin right after `Occlusion.esp` (last
line of `plugins.txt`/`loadorder.txt`; profile backups in `E:/Zenderal-backups/2026-10-28-vyn-full-extend/`).
`tools/00 --with-self` on the live load order afterwards: every LOD4/LOD8 chunk with Unified Water fully covered, 3
cells left at LOD16/32, the inland `no-water` cells near (−31, 34) whose `XCLW` Unified Water rejects (not sea). A
rerun of `tools/00` → `tools/01` reproduces the deployed `.esp` byte for byte (`tools/00` leaves our own plugin out,
so the holes stay visible to it). Unified Water rebuilds its cache on the next launch (load order changed).
Unverified in game.

**First test (2026-10-28): still gaps.** The launch rebuilt the cache with this plugin. Decoded `Vyn_cache.wc` has
24,700 LOD4 cells, matching `tools/00 --with-self` exactly, with bounds −96, −64, so the data side is done. The
curator's video shows whole rectangles of sea vanishing and returning as the camera turns. That is culling, not missing
data. [`ZenWaterTrace`](ZenWaterTrace.md) found the cause: Unified Water assumes 0-aligned LOD chunks, and Vyn's grid
starts at −69, −55. It is fixed at runtime by [`UnifiedWaterGridFix`](UnifiedWaterGridFix.md), verified in game
2026-10-28. **Both are needed:** this plugin supplies the data, the DLL puts it on the right chunks.
